How a cycle works

Every step is run by Claude; traffic runs in GitHub Actions against the live site.

TrafficSimulated shoppers browse the live shop; events go to GA4 and our log.
EvaluateRunning tests checked against rules R1–R7: ship, stop or continue.
AnalyseFunnel, device, page and price-band cuts from the event log.
HypothesiseObservation → hypothesis → change → metric, scored ICE.
Build & QAVariant coded behind a feature flag, rendered and checked.
DeployCommit → GitHub Pages; next traffic run queued.

Decision rules

Fixed in advance; the engine cannot ship a change that fails them.

Min. exposed visitors per variant400
Max. per variant (then stop)4000
Significance level α0.01
Min. probability to beat control0.95
SRM alarm p0.001
Guardrail harm α0.1
Max. concurrent tests3
  1. R1 Validity: if the sample-ratio-mismatch p-value < srm_p_threshold the test is INVALID — pause and investigate, never ship.
  2. R2 Patience: no decision before every variant has min_exposed_per_variant exposed visitors. alpha is 0.01 (not 0.05) because results are checked after every traffic run (sequential peeking).
  3. R3 Ship: primary metric uplift > min_relative_uplift, two-sided p < alpha AND probability-to-beat-control >= min_prob_to_beat.
  4. R4 Guardrails: do not ship if any guardrail metric is worse with p < guardrail_harm_alpha, or its point estimate drops more than guardrail_max_relative_drop (sanity cap) — unless the primary metric IS that guardrail.
  5. R5 Kill: stop if the primary metric is significantly worse (p < alpha), or max_exposed_per_variant is reached without a ship decision (inconclusive -> keep control: simplest wins).
  6. R6 Isolation: at most max_concurrent_experiments running, and never two running experiments that change the same feature key or share an exposure page.
  7. R7 Ship = merge the winning variant's features/css into site/config/site-config.json, log to docs/decision-log.md; the change becomes the new control.
